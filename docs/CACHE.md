# Кешування операцій читання

Код: [cache.py](../smartbite_python_backend/smartbite_python_backend/cache.py),
`list_plans` у [main.py](../smartbite_python_backend/smartbite_python_backend/main.py).
Інфраструктура: [terraform/cache.tf](../terraform/cache.tf).

## Що кешується і як

Найнавантаженіша операція читання — **`GET /plans`** (список планів): 4 з 9 читань у
сценарії навантаження. Схема **cache-aside**:

```
запит GET /plans?limit=50&offset=0
  └─ GET plans:list:50:0 у Redis
       ├─ є (TTL не сплив) → повернути              X-Cache: HIT
       └─ немає → SELECT … ORDER BY id DESC LIMIT 50 у PostgreSQL
                  → SET plans:list:50:0 <json> EX 30 → повернути   X-Cache: MISS
```

* **TTL = 30 с** (`CACHE_TTL_SECONDS`, Terraform `cache_ttl_seconds`).
* **Fail-open**: якщо Redis недоступний (таймаут 200 мс), запит іде в базу і сервіс
  не падає.
* Частка влучань рахується двома способами. k6 бачить заголовок `X-Cache` (метрика
  `cache_hit`). Застосунок веде лічильники в Redis, спільні для всіх екземплярів:
  `GET /make-server-fd5d4174/cache/stats`, скинути — `DELETE` на ту саму адресу.

### Чому Redis, а не кеш у пам'яті процесу

Redis працює окремим ECS-сервісом (`redis:7.4-alpine`) у приватних підмережах, адреса
`redis.smartbite.local` через Cloud Map. Доступ до нього є лише з security group
застосунку. Це безкоштовна альтернатива ElastiCache (~$12–16/міс).

Кеш у пам'яті процесу при 3 екземплярах означав би 3 незалежні кеші:

* кожен екземпляр окремо робить MISS і ходить у базу, тож частка влучань утричі менша;
* екземпляри віддають **різні** версії списку. Користувач, якого ALB кидає між
  екземплярами, бачить, як щойно створений план то з'являється, то зникає;
* інвалідацію неможливо зробити: запис на екземплярі A не може очистити пам'ять B і C;
* новий екземпляр, створений автоскейлером, стартує з порожнім кешем.

Спільний Redis — одна копія даних для всіх екземплярів, і інвалідація одним `DEL`.

## Як прогнати порівняння

Кеш вимикається без передеплою заголовком `X-Cache-Bypass: 1` (його додає `CACHE=off`):

```bash
URL=$(terraform -chdir=terraform output -raw app_url)
k6 run -e BASE_URL=$URL -e CACHE=off loadtest/smartbite.js
# дочекатися повернення до 1 задачі (~20 хв), скинути лічильники:
curl -X DELETE $URL/make-server-fd5d4174/cache/stats
k6 run -e BASE_URL=$URL -e CACHE=on  loadtest/smartbite.js
curl $URL/make-server-fd5d4174/cache/stats
```

Навантаження на базу — графік «База даних» на панелі (RDS CPU, ReadIOPS) за час прогону.

коли запитів якраз не було.

### Висновок

* Кеш свою роботу зробив: **запитів списку до бази стало у 26 разів менше**, а медіана
  читань впала майже вдвічі.
* На загальну латентність і на базу він майже не вплинув, і це закономірно. **Вузьке
  місце SmartBite — CPU застосунку, а не база.** `POST /generate-plan` займає секунди
  на 0.25 vCPU і завантажує процес на 86–100 %. Читання з кешу теж чекають на вільний
  процесор у тому самому процесі. База завантажена лише на 4 %: запит списку дешевий
  (50 рядків за індексом).
* Загальний p95 з кешем навіть трохи гірший (8.3 с проти 6.0 с). Його визначають
  записи, а ті залежать від того, наскільки швидко з'явились нові задачі. В обох
  прогонах друга задача з'явилась через ~5–6 хв після перетину порогу, тож різниця
  в межах розкиду між прогонами.
* Що допомогло б насправді: винести генерацію плану в чергу й окремий обробник
  (бонус 6), збільшити CPU задачі або кешувати сам результат генерації для однакових
  параметрів. Для сервісу, де вузьке місце — база, той самий кеш дав би значно
  більший ефект.

## Актуальність даних

Записи не інвалідують кеш, лише TTL. Тому **після створення плану клієнт до 30 с
(TTL) може не бачити його у `GET /plans`**. Сам план за `GET /plans/{id}` доступний
одразу, бо цей ендпоінт не кешується.

Як зменшити цей час:

1. **Менший TTL** (наприклад, 5 с). Дані свіжіші, але частка влучань нижча, і база
   отримує більше запитів. TTL 1 с практично знищує користь кешу. TTL 1 год означає,
   що користувачі годину бачать застарілий список.
2. **Інвалідація при записі**: у `generate_plan` і `delete_plan` після `commit()`
   виконати `DEL plans:list:*` (або тримати версію списку `plans:ver` і робити її
   частиною ключа: `INCR plans:ver`). Застарілість тоді ≈ 0, але за профілю 1:9 кеш
   скидається після кожного запису, і частка влучань падає.
3. **Компроміс**: інвалідація + TTL як страховка, якщо `DEL` не виконався
   (наприклад, процес упав між `commit` і `DEL`).

### Лавинне звернення (cache stampede)

Коли популярний ключ спливає, усі одночасні запити отримують MISS і разом ідуть у базу.
Тут ризик невеликий: один дешевий запит раз на 30 с. Для важчих запитів допомагають:
блокування на перебудову (`SET lock NX EX 5`: перебудовує один, решта віддає старе
значення або чекає), випадковий розкид TTL (jitter), а також оновлення ключа у фоні
до того, як він спливе.
